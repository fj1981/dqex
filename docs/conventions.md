# 开发约定（Conventions）

本文件记录本项目反复踩坑后沉淀的工程约定，所有涉及「状态拆分 + 多视图同步」的改动都须遵守。

---

## 1. 改动前的强制三步（先想清楚再写代码）

任何涉及多组件状态联动、选表/选库/映射这类功能时，**禁止**直接上手改一个文件就交付。必须在动笔前完成：

1. **列清每个 state 的唯一职责与读写方**
   - 谁写（唯一写入点）、谁读、默认值是什么。
   - 不同概念（如「映射关系」与「用户勾选的库」）**必须是独立 state**，绝不要用同一个 state 推导出两个语义。
2. **模拟关键状态下的渲染值**
   - 至少覆盖：`初始` / `数据加载中（列表为空）` / `加载完成` / `用户操作后`。
   - 尤其注意「列表为空时 checkbox 的回退判定逻辑」（如 `total===0` 时按 `selectedDBs.includes` 判定），它常被默认值污染。
3. **对齐前后端字段语义**
   - 前端字段格式（如 `"源库.表"` 限定名）与后端解析（如按裸名过滤、库对由 `databases` 提供）必须一次性核对，而不是只在组件内部修补。

> `tsc` 通过 ≠ 逻辑正确。编译通过只是底线，不等于状态建模正确。

---

## 2. 状态建模禁止项

- ❌ 用「另一个 hack 去补上一个 hack」。每次改动若引入新副作用，先回退思考根因。
- ❌ 把「展示用合并」和「状态默认值」混为一谈。展示合并属于渲染层，默认值属于 state 初始化，二者解耦。
- ❌ 让派生数据反写父状态造成循环（如 `selectedDBs` 从 `databases` 推导，又用 `selectedDBs` 去填 `databases`）。
- ✅ 状态默认值保持「最小/空」，用户操作后再填充。不要为了「让 UI 看起来对」而预填全量。

---

## 3. 对比（compare）选表功能的具体约定

该模块是历史重灾区，遵守以下模型：

| 概念 | 来源 | 职责 | 默认 |
|---|---|---|---|
| 树节点名 | 映射前的**源库名** | 库节点永远显示源库名，映射改名不改变节点名 | — |
| 树节点下的表 | `源库表 ∪ 该源库映射到的目标库表`（按裸名去重） | 展示合并；`dbMapping` 为空时默认同名映射 | — |
| `databases` | 用户勾选库/表后填充 | 代表「要对比的库对」，运行时源用源库、目标用映射库 | **空** |
| `selectedDBs` | 用户勾选的库 | 仅代表用户勾选的库，与映射关系解耦 | **空** |
| 右侧 `selected` | 用户勾选的 `源库.表` 限定名 | 严格等于用户勾选，不强制并入目标库独有表 | 空 |
| `startRun` | 用户勾选的表 | 严格只对比用户勾选的表，不自动补全目标库独有表 | — |

要点：
- 目标库独有表在树中可勾选（带「仅目标库有」标记），但**不强制并入选中区**。
- 进入选表页时，`cy_licgen` 这类同名映射库应直接合并显示全部表（由树内部默认同名映射保证），**不依赖 `databases` 预填**。

---

## 4. 全链路数据流追踪

改任何「数据持久化 / API 通信 / 多层架构」的功能时，遵循：
1. 前端表单 → 前端预览 → API 请求 → 后端存储 → 后端生成，每一点都检查，不只改用户提到的那一个点。
2. 检查所有写入路径（Create / SaveDraft / Publish 等）同步同一字段。
3. 前后端一致性：后端加字段，前端 TypeScript 接口、预览/展示逻辑同步更新。
4. 业务逻辑意识：草稿不应在已上线语境生效，主动过滤 `published_version>0` 等业务规则。

---

## 5. 提交前自检清单

- [ ] 每个 state 有唯一写入点，职责不重叠
- [ ] 模拟了「初始 / 加载中 / 加载后 / 操作后」四种状态渲染
- [ ] 前后端字段语义对齐（格式、过滤方式）
- [ ] 没有用 hack 掩盖 hack
- [ ] 默认值最小（不预填全量）
- [ ] `tsc --noEmit` 通过，且逻辑（非仅编译）自洽
